## Jadi, sebenarnya ini ngapain?

Access token itu **kartu identitas** user. Sampai sekarang kartunya disegel dengan **satu kunci rahasia** (HS256). Kunci itu dipakai untuk membuat segel **dan** memeriksanya. Selama yang memeriksa hanya Auth, itu tidak masalah. Tapi sebentar lagi Application Service juga harus memeriksa kartu. Kalau kunci yang sama dibagikan ke sana, service itu juga bisa **membuat** kartu palsu, termasuk kartu ADMIN.

Sekarang kuncinya dipisah:

- **Kunci privat** (hanya Auth yang pegang) untuk **membuat** segel (RS256).
- **Kunci publik** (boleh dilihat siapa saja) untuk **memeriksa** segel. Auth membagikannya di `/.well-known/jwks.json`.

Isi kartunya juga dirapikan:

| Sebelum | Sesudah |
|---|---|
| `sub` = username (bisa berubah) | `sub` = **UUID user** (tidak pernah berubah, cocok dengan `owner_user_id` di Application Service) |
| Tidak ada penerbit atau tujuan | `iss = careertrack-auth`, `aud = careertrack-api` |
| Tidak ada ID sesi | `sid` = ID sesi login, tetap sama walaupun token di-refresh. Ini dasar untuk "logout langsung berlaku di semua service" (tahap C2). |
| Tidak ada ID kunci | Header `kid`, supaya kunci bisa diganti tanpa downtime |

**User yang sedang login tidak terganggu.** Selama 7 hari, Auth tetap menerima token lama. Begitu user me-refresh, ia otomatis mendapat token baru.

## Keputusan teknis dan alasannya

### 1. Kunci dipilih dari header, dan setiap kunci hanya cocok untuk satu jenis algoritma
```
alg = RS256 dan kid = kid kita   → public key RSA
alg = HS256/HS384/HS512           → secret lama (hanya kalau JWT_SECRET masih di-set)
selain itu (termasuk alg: none)  → ditolak sebelum signature dicek
```
Ini menutup serangan **algorithm confusion**: penyerang membuat token HS256 dengan public key (yang memang publik) sebagai "secret". Karena HMAC **hanya** pernah memakai secret lama, bukan kunci RSA, token seperti itu pasti gagal. Ada test khusus untuk ini.

### 2. Bug yang ditemukan test: token lama ternyata HS512
Kode lama memanggil `signWith(key)` **tanpa menyebut algoritma**, sehingga JJWT memilih algoritma dari panjang secret:

| Panjang secret | Algoritma |
|---|---|
| 32–47 byte | HS256 |
| 48–63 byte | HS384 |
| ≥ 64 byte | **HS512** |

Versi pertama kode baru hanya menerima HS256. Integration test langsung gagal (token test ternyata HS384), dan gladi migrasi membuktikan token di laptop **HS512**. Kalau lolos ke production, semua user akan ter-logout saat deploy. Sekarang ketiga varian HMAC diterima, tapi tetap hanya dengan secret lama.

### 3. `iss`/`aud` hanya diwajibkan untuk token RS256
Token lama tidak punya `iss`/`aud`, sehingga mewajibkannya akan menolak semua token lama. Token **baru** wajib punya keduanya, dan pemeriksaan ini terbukti berfungsi: kalau dimatikan, test `wrongIssuer` dan `wrongAudience` langsung gagal.

### 4. Token baru wajib `sub` UUID; token lama wajib `sub` username
`subjectMatches` membedakan keduanya lewat ada atau tidaknya `iss`. Token RS256 dengan `sub` berisi username ditolak, sehingga penyerang tidak bisa memakai jalur lama dengan kunci baru.

### 5. `kid` = thumbprint kunci (RFC 7638)
Tidak perlu konfigurasi ID kunci terpisah. Kalau kunci diganti, `kid` otomatis ikut berubah, dan token yang ditandatangani kunci lama ditolak karena `kid`-nya tidak dikenal.

### 6. `sid` dipertahankan saat refresh
Satu login = satu sesi. Saat refresh token dirotasi, `session_id` yang sama ikut disimpan di baris baru. Refresh token lama (sebelum V14) belum punya sesi, jadi diberi sesi baru saat refresh pertama.

### 7. Kunci test dibuat di memori
`ContextCustomizerFactory` (didaftarkan lewat `META-INF/spring.factories`) membuat satu kunci RSA per JVM untuk semua Spring test context. Satu kunci dipakai bersama supaya cache context Spring tetap efektif. Tidak ada mode "kunci sementara" di kode production.

## Verifikasi

### Test: **169/169** (sebelumnya 135)
- `JwtKeysTest` (10): format PEM, base64, `\n` literal, `kid` stabil, JWKS **tanpa** parameter privat (`d`, `p`, `q`, ...), menolak kunci kosong, < 2048 bit, PKCS#1 (dengan petunjuk `openssl pkcs8`), kunci EC, dan sampah (tanpa menampilkan isinya di pesan error)
- `JwtServiceImplTest` (22): format token sesuai kontrak; aturan lama (tokenVersion, type, akun suspend, user lain); **serangan**: `iss`/`aud` salah, kunci lain dengan `kid` kita, `kid` tidak dikenal, `alg: none`, HS256 dengan public key sebagai secret; **transisi**: token lama diterima selama secret ada (termasuk HS512), ditolak setelah secret dihapus, token RS256 dengan `sub` username ditolak
- `JwtPropertiesValidationTest` (11): private key wajib, secret lama opsional tapi tetap divalidasi
- `MeEndpointIntegrationTest` (+4): JWKS publik dan bisa memverifikasi token dari login; token login berlaku di `/me`; refresh mempertahankan `sid` dan menyimpannya di DB; token HS lama masih berlaku selama transisi

### Cek balik
Pemeriksaan `iss`/`aud` dimatikan sementara, dan test `wrongIssuer_isRejected` serta `wrongAudience_isRejected` langsung gagal.

### Gladi migrasi dengan aplikasi sungguhan
Auth **lama** (port 8081) dan Auth **baru** (port 18999) memakai DB lokal yang sama:

| Langkah | Hasil |
|---|---|
| Login di Auth lama | Token **HS512**, `sub` = username |
| Auth baru start | Health 200, migrasi V14 sukses |
| `/me` dengan token lama di Auth baru | **200** |
| Refresh dengan token lama | Token **RS256**, `kid`, `sub` = UUID, `sid`, `iss`, `aud`, `username` |
| Refresh token lama dipakai lagi | **401** (rotasi tetap berlaku) |
| Login di Auth baru | RS256 + `session_id` tersimpan di DB |
| JWKS | `kty=RSA alg=RS256 use=sig`, **tanpa `d`**, `Cache-Control: max-age=300, public` |
| Verifikasi signature **hanya** dengan JWKS | **Valid** |
| Token baru dipakai ke Auth lama | 401 (wajar, Auth lama tidak kenal RS256) |

### Start tanpa kunci
```
Property: jwt.privateKey
Reason: must be set (provide the JWT_PRIVATE_KEY environment variable)
```

## Urutan deploy (penting)

1. **Pasang `JWT_PRIVATE_KEY` di EC2 lebih dulu.** Langkahnya ada di runbook pribadi. Kunci dibuat **langsung di server** dan tidak pernah ditampilkan.
   - Tambahkan `JWT_PRIVATE_KEY: ${JWT_PRIVATE_KEY:?missing}` ke compose Auth.
   - **Biarkan `JWT_SECRET`** tetap ada, karena ia memeriksa token lama selama 7 hari.
2. Merge PR ADR (dokumentasi).
3. Merge PR ini. CI mem-publish image, lalu timer EC2 men-deploy Auth baru.
4. Verifikasi di server: `curl -s http://127.0.0.1:18081/.well-known/jwks.json` menampilkan satu key RSA. Login di web harus tetap jalan, dan user yang sudah login tidak ter-logout.
5. **Catat tanggal deploy.** Tujuh hari setelahnya: tahap D (hapus jalur HMAC lama dan `JWT_SECRET`).

**Kalau deploy gagal:** skrip CD otomatis rollback ke image lama. User yang sempat mendapat token RS256 harus login ulang, karena Auth lama tidak mengenal RS256. Ini bisa diterima.

## Batasan dan langkah berikutnya

- **Tahap C2:** tabel `token_revocations` dan endpoint internal, supaya logout langsung berlaku di service lain (memakai `sid` yang sekarang sudah ada).
- **Tahap D (+7 hari):** hapus jalur HMAC lama, `JWT_SECRET`, dan pencarian user lewat username.
- Claim `roles` belum ditambahkan. Akan ditambahkan kalau Application Service butuh otorisasi kasar berdasarkan role.
- Kunci disimpan sebagai environment variable. Pindah ke file yang di-mount atau secret manager bisa dilakukan belakangan tanpa mengubah kode (cukup mengisi `JWT_PRIVATE_KEY`).
